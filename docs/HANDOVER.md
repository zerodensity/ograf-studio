## What this is

A browser-based, visual (WYSIWYG) editor for authoring **OGraf**-compliant HTML5 broadcast graphics templates (lower thirds, scoreboards, tickers) — think "Adobe Animate crossed with a broadcast graphics CG system." OGraf is an EBU (European Broadcasting Union) open standard letting HTML5 graphics templates run interchangeably across playout vendors. The spec: https://ograf.ebu.io/v1/specification/docs/Specification.html

The product's north star is **Loopic** (https://app.loopic.io), a commercial tool that does this for other CG systems (CasparCG, SPX, LiveOS) and recently added OGraf export — we're taking UX/feature inspiration from it (no copied code) and filling a real gap: the existing open-source OGraf tools (`ograf-devtool`, `ograf-server`) only _play_ pre-built templates, neither lets someone author one visually.

Full research context, spec details, and the original architecture reasoning live in `docs/PLAN.md`. This document covers what's **actually been built**, how it works, and what's genuinely next.

## Stack (as actually installed — deviates from the original plan in a few places)

- **Package manager: npm workspaces**, not pnpm. The original plan called for pnpm, but `corepack enable` failed on this Windows machine (no permission to write to `C:\Program Files\nodejs\`), and installing pnpm via `npm install -g pnpm` worked but didn't stay on `PATH` across separate Bash tool calls (each call is a fresh shell). npm workspaces was the pragmatic swap — functionally equivalent for our needs, zero extra tooling risk. Root `package.json` has `"workspaces": ["apps/*", "packages/*"]`.
- **React 19, Vite 8, TypeScript ~6.0** — newer than the plan's "React 18 + Vite 5". `npm create vite@latest` scaffolded these current versions; no reason was found to pin older ones.
- **oxlint**, not ESLint — fast Rust-based linter, zero-config, came from the Vite scaffold. Run via `npm run lint` at the root or in `apps/editor`. It's quiet on success (no output, exit 0) — don't mistake silence for "didn't run."
- **Zustand 5 + Immer** for state, **react-moveable** for canvas drag/resize/rotate, **GSAP 3** for animation (both in-editor and eventually in exported templates).
- **Prettier** configured at the root (`.prettierrc.json`) but not yet wired into a pre-commit hook or CI.

## Data model (read `packages/scene-model/src/types.ts` for ground truth)

```
Project
 ├─ id, name, description, version, author, mainCompositionId
 └─ compositions: Composition[]

Composition
 ├─ id, name, width, height, backgroundColor
 ├─ frameRate: number                — frames/sec the timeline is authored against (default 25)
 ├─ layers: Layer[]
 ├─ keyframes: Keyframe[]            — ordered; each is a full pose snapshot point (NOT "Step" — renamed, see below)
 ├─ transitions: Transition[]        — edges between consecutive keyframe pairs only (a linear chain, not an arbitrary graph)
 ├─ dataFields: FieldDefinition[]    — dynamic inputs the template accepts at runtime (Phase 3)
 └─ customActions: CustomActionDefinition[]   — author-defined OGraf customActions (Phase 3, declarative metadata only — nothing runtime-side triggers these yet, no Phase 4 harness exists)

Keyframe
 ├─ id, name
 └─ isOutro: boolean                 — at most one per Composition; marks where stopAction would land (not wired to anything yet — no export exists)

Transition
 ├─ id, fromKeyframeId, toKeyframeId
 ├─ durationFrames: number           — NOT milliseconds (see "Frames, not ms" below)
 └─ easing: 'linear' | 'ease-in' | 'ease-out' | 'ease-in-out'

Layer
 ├─ id, name, isVisible, isGuide
 ├─ poses: Record<keyframeId, LayerTransform>   — one full pose PER KEYFRAME; every layer has an entry for every keyframe, always (invariant maintained by the store)
 ├─ element: RectangleElement | TextElement | ImageElement   — content/styling, NOT keyframe-varying (only the transform is animated; text/fill/src etc. are constant across keyframes — a deliberate scope cut)
 └─ binding: LayerBinding | null      — { fieldId, targetProperty } when a data Field drives one of this layer's element properties; see "Data binding" below

LayerTransform
 └─ x, y, width, height, rotation, opacity, transformOriginX, transformOriginY

FieldDefinition                                        — one dynamic input, compiles into the manifest's `schema`
 ├─ id, key (unique, the JSON Schema property name), label
 ├─ type: 'text' | 'textarea' | 'number' | 'boolean' | 'color' | 'image-url'
 ├─ defaultValue: string | number | boolean
 └─ required: boolean

CustomActionDefinition                                  — compiles into `manifest.customActions[]`
 └─ id, actionId (unique slug), name, description
```

**Key design decision — discrete Keyframes, not a continuous frame-by-frame timeline with arbitrary code**: this was the single most important call in the original plan (see `docs/PLAN.md`, "The Steps-vs-frames decision"). OGraf's runtime contract (`stepCount`, `playAction({goto/delta})`) is inherently a discrete, numbered-pause-point model. Every Keyframe = a full pose for every layer; the animation between two adjacent Keyframes is authored as one Transition (single duration + easing, applies to every layer's pose change in that span — not per-property). This makes templates "correct by construction" against OGraf, at the cost of not supporting Flash/Loopic-style arbitrary per-frame scripting (deliberately deferred).

## Data binding (Phase 3)

A `Layer.binding` (`{ fieldId, targetProperty }`) is the whole mechanism — deliberately simpler than Loopic's two-step "key on layer + separate TDBuilder mapping": since our layers already have stable ids, the binding just lives directly on the layer, no join table. `targetProperty` is restricted per element type via `BINDABLE_PROPERTIES` in `apps/editor/src/state/dataBinding.ts` (text → `content`/`color`; image → `src`; rectangle → `fill`) — deliberately just the "content surface" of each element, not arbitrary properties.

**Design-time preview is non-destructive by construction.** The Data panel's "Test Data" inputs write into `testDataStore` (fieldId -> value), a separate, non-persisted, non-undo-able store — never into the document. `dataBinding.ts`'s `resolveEffectiveElement(layer, testValues)` is a pure function that returns the authored `element` unchanged unless a bound field has a live test value, in which case it returns a _copy_ with that one property overridden. `LayerNode.tsx` renders through this function, not `layer.element` directly. This means the canvas shows "what it would look like with this data" while the Inspector's own content field always shows the untouched authored default — verified explicitly: setting a test value to "Jane Smith" updated the canvas immediately while the Inspector's Content field kept showing the original authored "Text".

This was a deliberate stand-in for what Phase 4's real preview harness now does properly (an actual `updateAction()` call against a real Custom Element) — `testDataStore`'s simulation is still there and still purely a Phase-3, UI-only, non-destructive canvas preview; it's separate from, and not replaced by, the Phase 4 harness described below.

## Runtime & export architecture (Phase 4)

**"Runtime is interpreted, not templated per-project"** (the plan's core Phase 4 decision, realized as designed): `packages/ograf-runtime/src/GraphicElement.ts` is one hand-written, generic `abstract class GraphicElement extends HTMLElement implements Graphic`. It reads a `static descriptor: CompiledGraphicDescriptor` off its own concrete subclass (Custom Elements can't take constructor args, so this is the only way to parameterize one) and interprets that descriptor — builds a `Map<layerId, HTMLElement>` in `connectedCallback`, drives one GSAP timeline via `buildRuntimeTimeline()`, and implements every `Graphic` lifecycle method (`load`/`dispose`/`updateAction`/`playAction`/`stopAction`/`customAction`/`goToTime`; `setActionsSchedule` returns `501` — not implemented, no schedule-authoring UI exists) by manipulating that map and timeline. Every method wraps its body in try/catch, returning `{statusCode: 550, statusMessage}` (OGraf's `GRAPHIC_ERROR_STATUS_CODE`) on a thrown error rather than letting it propagate.

The **same class, from the same npm-workspace source**, drives two call sites — this is what guarantees preview and export can never diverge:

1. **In-app preview** (`ograf-runtime`'s `registerGraphicElement(descriptor)`, called from `PreviewExportPanel.tsx`): dynamically declares `class extends GraphicElement { static descriptor = ... }` and registers it under a counter-suffixed tag name (`customElements.define` can't be called twice for the same name, and the panel rebuilds on every composition edit).
2. **Real export** (`apps/editor/src/state/exportPackage.ts`'s `generateMainJs`): the pre-built, self-contained `packages/ograf-runtime/dist/graphic-runtime.js` (GSAP inlined, zero external imports — see that package's `vite.config.ts`, library mode) is embedded via a Vite `?raw` import, then a static `class ExportedGraphic extends GraphicElement { static descriptor = {...} }; export default ExportedGraphic;` is appended as plain text in the same module — valid ESM because the runtime bundle's own trailing `export {...}` statement means `GraphicElement` is already in module scope, no import needed.

**Compiling a Composition** (`packages/codegen`): `compileDescriptor(composition)` resolves each layer's `binding.fieldId` to the bound field's `key` (stored on the compiled layer as `dataKey`, since the runtime only ever sees plain data objects keyed by field `key`, never field ids) and drops `isGuide` layers entirely (guides are an authoring-only concept). `assembleManifest(project, composition, descriptor)` builds the actual `OGrafManifest` (`stepCount` = keyframe count, `schema` from Phase 3's `compileDataSchema`, `customActions`, `renderRequirements.accessToPublicInternet: false` by default). `packages/validation`'s `validateManifest()` runs the assembled manifest through ajv against a **hand-authored local copy** of the OGraf manifest JSON Schema (`ografManifestSchema.ts` — not fetched live from the EBU URL; if the real spec schema changes, this local copy needs manual updating).

**Export packaging** (`exportProjectAsZip`): builds the manifest + `main.js`, zips them as `{manifest.id}.ograf.json` + `main.js` via JSZip, and saves via `saveBlobToFile` (File System Access API `showSaveFilePicker`, falling back to an `<a download>` click).

**Verified as the project's actual compliance gate** (see gotcha #6 below for _how_, since the obvious "click Export and inspect the file" path doesn't work in this environment): a real composition (bound text layer, two keyframes with an outro flag) was compiled, the assembled manifest passed ajv validation, the zip round-tripped through `JSZip.loadAsync` byte-for-byte, and — the important part — the generated `main.js` text was loaded as a **standalone dynamic `import()` of a blob URL**, completely independent of the app's own `PreviewExportPanel` code path, and its `Graphic` interface was driven directly: `load()` correctly applied the bound field's data, `playAction({delta, skipAnimation: true})` correctly advanced `currentStep` and re-sought the timeline, `updateAction()` correctly re-rendered new data, `stopAction()` succeeded, `customAction()` correctly returned `404` for an unknown id, and `dispose()` succeeded. This proves the exported package is genuinely self-contained and spec-correct, not just "correct because it's still running inside the editor's own module graph."

## Naming history (matters if you find old references)

Originally called **"Step"** everywhere (`Step`, `activeStepId`, `addStep`, `.timeline-step-marker`, etc.) — this matched OGraf's own `stepCount` terminology. The user later asked to rename to **"Keyframe"** for a more NLE-familiar feel, and it was renamed _everywhere_: types, store actions, CSS classes, UI labels. If you ever see "Step" in code, it's either (a) something missed in the rename — grep for it, or (b) the literal DOM `<input step={...}>` attribute (unrelated, don't touch). The rename was verified complete with `grep -rniE "\bstep[a-z]*\b"` across `apps/editor/src` filtering out the HTML attribute.

## Frames, not milliseconds

Originally `Transition.duration` was milliseconds. The user asked to work in **frames** instead (broadcast/NLE convention). Now:

- `Composition.frameRate` (default 25fps) is the single source of truth for frame↔time conversion.
- `Transition.durationFrames` is an integer frame count.
- **GSAP itself only ever works in seconds** — frame↔second conversion happens at exactly one boundary: inside `masterTimeline.ts`'s `buildMasterTimeline()` and inside `Stage.tsx`'s rebuild effect / `TimelineController`. Nowhere else in the app should you see a raw millisecond value for animation timing. `keyframeTiming.ts`'s functions all operate purely on integer frame numbers.

## State management map

- **`projectStore`** — the document itself (`project: Project`) plus `activeCompositionId` and `activeKeyframeId` (which keyframe's pose the Inspector/canvas currently shows for editing — this is a deliberately _separate, explicitly-committed_ piece of state from the timeline's continuously-updating playhead; see "Canvas & timeline architecture" for why merging them was tried and reverted). Actions: layer CRUD (`addLayer`/`removeLayer`/`updateLayerTransform`/`updateLayerElement`/`renameLayer`/`toggleLayerVisibility`/`toggleLayerGuide`/`reorderLayers`), keyframe CRUD (`addKeyframe`/`removeKeyframe`/`renameKeyframe`/`setKeyframeOutro`/`setActiveKeyframe`), `updateTransition`. Also exports `getActiveComposition(project, compositionId)` and `getLayerPose(layer, keyframeId)` as plain helper functions (not hooks) — used from non-component code (historyStore, TimelinePanel's imperative handlers).
- **`selectionStore`** — just `selectedLayerId`. Pure UI state, not part of the document, not undo-able.
- **`timelineStore`** — `currentFrame` (float, updates every GSAP tick during scrub/playback — **only the Timeline panel subscribes to this**, deliberately, so high-frequency updates don't cascade into canvas/Inspector re-renders fighting GSAP's imperative DOM writes), `isPlaying`, `durationFrames`, and `controller: {seek, play, pause} | null` which `Stage.tsx` registers.
- **`historyStore`** — not a hook-based store, just module-level state + a `useProjectStore.subscribe()` side effect (registered by importing the module — `App.tsx` imports it for the keyboard handler, which is what triggers the subscription to exist). Exports `undo()`, `redo()`, `resetHistory()` as plain functions, called from `App.tsx`'s keydown handler and `Menubar.tsx`'s New/Open handlers. Debounces rapid edits (500ms) into one undo step; explicitly flushes the pending snapshot when `undo()` is called so even a very recent edit is undo-able immediately.
- **`fileIO`** — not a store, just functions: `saveAutosave`/`loadAutosave` (localStorage), `saveProjectToFile`/`openProjectFromFile` (File System Access API with graceful fallback to `<a download>`/`<input type=file>` on unsupported browsers).

## Canvas & timeline architecture — read this before touching `Stage.tsx` or `TimelinePanel.tsx`

This is the trickiest part of the codebase and had two real race-condition bugs during development (both fixed, but understanding _why_ they happened will save you from reintroducing them or their cousins).

**The pattern**: `Stage.tsx` owns a `Map<layerId, HTMLDivElement>` of the actual layer DOM nodes. GSAP animates these nodes _imperatively_ (bypassing React) for performance — same pattern as `react-moveable`'s drag/resize/rotate handlers (mutate `target.style` directly during the gesture, only call a Zustand action to _commit_ the final value once the gesture ends). React only re-renders the layer's `style` when `activeKeyframeId` (a deliberately low-frequency store value) changes, and by design that always converges to the same values GSAP already animated to, so there's no visible fight between imperative and declarative updates — **as long as you don't wire high-frequency state (like `currentFrame`) into anything the canvas's React render reads.**

**`masterTimeline.ts`'s `buildMasterTimeline()`** builds _one_ paused GSAP timeline spanning every keyframe in sequence (not one-tween-per-transition rebuilt on each navigation — that was the Phase 2 approach and got replaced when the "NLE timeline" request came in). It:

1. Snaps every layer to Keyframe 0's pose via `gsap.set()` first — necessary because GSAP's `.to()` lazily captures its "from" value from whatever the DOM currently shows, which could be stale/wrong without this.
2. Adds a `tl.addLabel(keyframeId, frame/frameRate)` at every keyframe's cumulative frame position.
3. Adds one `tl.to(el, {...pose, duration, ease}, startSeconds)` per layer per transition segment.

`Stage.tsx` rebuilds this whenever `composition` changes (any edit at all — cheap enough at this scale to not bother diffing), re-seeks it to wherever the playhead currently was (so an unrelated edit doesn't visually snap the canvas back to frame 0), and registers a `TimelineController` (`seek`/`play`/`pause`) into `timelineStore` that `TimelinePanel.tsx` drives.

**Race condition #1 (fixed)**: an action that both mutates the composition _and_ immediately tries to seek (e.g. clicking "+ Keyframe") was calling `controller.seek()` using the _stale_ controller — captured in a closure from before Stage's rebuild effect ran — so the seek landed on the old (shorter) timeline and got clamped. Fix: route every "jump to a keyframe" action through a single `useEffect` in `TimelinePanel.tsx` that fires when `activeKeyframeId` (or `composition`, or `controller`) changes, rather than seeking at the point of the action.

**Race condition #2 (fixed)**: the first fix above still raced, because `setController(...)` called _inside_ Stage's rebuild effect only _queues_ a follow-up render — it doesn't retroactively update the `controller` value `TimelinePanel`'s effect closure already captured from the pre-rebuild render. Fix: `controller` itself had to be added to that effect's dependency array too, so it gets a second, correct chance to fire once the fresh controller actually lands. **Both fixes are documented in code comments at the exact call sites** (`TimelinePanel.tsx`, the big comment above the `useEffect` watching `[activeKeyframeId, composition, controller]`) — read those comments before changing this logic.

**Why `activeKeyframeId` (projectStore) and `currentFrame` (timelineStore) are separate, not derived from each other**: an earlier design tried deriving "which keyframe is active" from `currentFrame` via nearest-match. This was reverted because `currentFrame` updates on every GSAP tick during playback (~60/sec), and if the canvas/Inspector's React render depended on a value that changes that often, it would re-render every frame and fight GSAP's imperative writes with jumpy, discrete (nearest-keyframe) values — visible stutter during playback. Keep them separate: `activeKeyframeId` changes only at discrete moments (keyframe click, add/remove, retime-drag-release, playback pause/complete); `currentFrame` changes continuously and only the Timeline panel's ruler/playhead should subscribe to it.

## What's explicitly NOT built (don't assume it exists)

- **No visual path editor** — `PathElement` is authored by pasting raw SVG `d` attribute data into a textarea; there's no interactive pen/bezier tool.
- **Custom Actions have no runtime behavior beyond acknowledgement** — `customAction()` returns `200` for any known action id with no scripted effect (declarative metadata only, per the Phase 3 scope cut) and `404` for unknown ids; no payload schema is modeled (see below).
- **No nested Compositions, no Lottie elements, no masks** — these were on the original Phase 5 list but not selected for this pass.
- **Element content (text/fill/image src) is NOT keyframe-varying** — only the transform animates. A layer's data binding also isn't keyframe-varying (one binding per layer, constant across all keyframes). If a future request wants "text changes between keyframes" or "binding changes between keyframes," that's a real data-model extension, not a bug fix. (Image-Sequence is a deliberate, narrow exception — its frame-advance is a self-contained loop, not a keyframe-driven property.)
- **Field key/customAction actionId uniqueness is enforced only at the point of edit** (`projectStore`'s `updateDataField`/`updateCustomAction` silently reject a rename that would collide) — there's no cross-cutting validation pass, and nothing stops two _newly created_ fields from momentarily existing with the store's auto-generated `field1`/`field2`-style keys colliding with a manually-typed one if edited in an unlucky order. Low risk, not hardened.
- **No payload schema for Custom Actions** — `CustomActionDefinition` is just id/name/description; OGraf's `customActions[].schema` (a payload shape, like `FieldDefinition[]` but for action arguments) isn't modeled yet.
- **`ui-kit` package is unused** — Inspector/Timeline/Data UI components live directly in `apps/editor`, not extracted into a shared package yet.
- **No tests** (no Vitest, no anything) — all verification so far has been manual, via the Browser pane tools.

## Environment gotchas — read before you burn time rediscovering these

1. **pnpm doesn't work in this environment.** `corepack enable` fails (no write permission to `Program Files\nodejs`), and `npm install -g pnpm` works but doesn't persist on `PATH` across separate Bash tool calls (each call is a fresh shell in this harness). Use npm workspaces (`npm install`, `npm run <script> --workspace <name>`, or `npm run <script> --workspaces --if-present` for all).
2. **Browser pane screenshots don't work in this session's environment** — `computer{action:"screenshot"}` and coordinate-based clicks reliably error with "the Browser pane is not displayed, so the page is not compositing frames." This may or may not be true in your session — try once early. If it's still broken, verify UI changes via `get_page_text`, `read_page` (accessibility tree, gives you `ref_N` handles for `computer`/`form_input`), `read_console_messages`, and `javascript_tool` (for direct DOM/state introspection) instead. This has been sufficient for all verification so far, including pixel-exact interpolation math checks.
3. **Same-script event-dispatch batching gives false negatives — this bit us repeatedly.** If you dispatch multiple synthetic DOM events (`pointerdown`/`pointermove`/`pointerup`, or several state-mutating actions) all within _one_ `javascript_tool` call, React 18's batching means later handlers in that same script can read _stale_ state/closures from before earlier handlers' effects have flushed — because effects and re-renders happen after the whole synchronous script finishes, not between dispatches within it. This produced several "looks broken" results during development that were actually just test methodology, confirmed by re-running the _exact_ same sequence as separate tool calls (letting React settle between each) and seeing it work correctly. **Always verify a suspected bug with properly separated tool calls before concluding the app is broken.** Conversely, don't assume every "stuck" result is this artifact — two of the fixes described above (the controller-staleness races) were real bugs found _despite_ this pattern, confirmed via direct GSAP state introspection (`tl.time()`, `tl.progress()`, `tl.paused()`) exposed temporarily on `window` for debugging, then removed.
4. **`computer` tool's coordinate-based clicks occasionally mis-hit** even when screenshots do work, seemingly due to viewport-size fluctuation between the `read_page` call that produced a `ref` and the click. When a `computer` click on a known-good `ref` doesn't seem to register, retry with a fresh `read_page` first, or fall back to `element.click()` via `javascript_tool` (also a legitimate simulated user action, just not through the `computer` tool).
5. **`react-hooks/exhaustive-deps` warnings from oxlint are sometimes intentionally wrong for this codebase's imperative-integration patterns** (Stage's rebuild effect, TimelinePanel's reseek effect, and now `PreviewExportPanel.tsx`'s instance-rebuild/data-form-reset effects). All have comments explaining exactly why the "missing" dependencies are deliberately omitted or included. Don't "fix" these without reading the comment first — the naive fix (adding the dep) was tried and caused real regressions (e.g., unrelated edits killing in-progress playback).
6. **The native `showSaveFilePicker()` dialog can't be driven by browser automation, and blocks the export/save flow forever if you click through the UI.** `saveBlobToFile`/`saveProjectToFile` (`apps/editor/src/state/fileIO.ts`) call `window.showSaveFilePicker()`, which pops a real OS-level file dialog outside the page's DOM — `computer` clicks, `Escape` key events, etc. can't reach it, and the button's `isExporting` state (or the async save call) just hangs indefinitely. **Don't click "Export .ograf.zip" (or "Save") through the Browser pane tools expecting it to complete** — reload the tab to recover, then verify the export logic directly instead: dynamically `import()` the app's own source modules straight from Vite's dev server (e.g. `await import('/src/state/exportPackage.ts')`, `await import('/@fs/C:/works/zd_ograf_editor/packages/ograf-runtime/src/index.ts')` for workspace packages not resolvable as bare specifiers from ad-hoc eval'd code) via `javascript_tool`, call `buildExportArtifacts`/`exportProjectAsZip`'s non-save-dialog pieces directly, and — for the strongest signal — build a `Blob`+`URL.createObjectURL` from the generated `mainJs` string and `import()` _that_ to drive the `Graphic` lifecycle standalone. This is exactly how Phase 4's compliance gate was actually verified.
7. **GSAP's real-time animated `tweenTo()` (used by `playAction`/`stopAction` without `skipAnimation: true`) can hang indefinitely in this Browser pane environment**, seemingly because its `requestAnimationFrame`-driven ticker doesn't reliably advance for a headless/automated tab — a `javascript_tool` call that `await`s an unflagged `playAction()` timed out after 30s on an animation that should take well under a second. This looks like an environment/automation quirk, not an app bug (the same call path with `skipAnimation: true` completes instantly and correctly). If you need to test animated (non-instant) playback timing specifically, wrap the await in a `Promise.race` against a short timeout so a hang doesn't eat your whole tool-call budget, and prefer `skipAnimation: true` for anything that's really just testing the lifecycle contract rather than the animation itself.
8. **A hand-authored test binding must use the exact `targetProperty` values `BINDABLE_PROPERTIES` offers** (`apps/editor/src/state/dataBinding.ts`: `'content'`/`'color'` for text, `'src'` for image, `'fill'` for rectangle) — **not** the element's `type` discriminant or any other guess. Driving `projectStore.setLayerBinding()` directly (bypassing the Inspector's dropdown, e.g. for scripted test setup) with an invalid value like `'text'` silently "succeeds" (no validation) but the binding then does nothing at render time, because `resolveBoundElement`/`resolveEffectiveElement` just spread `{ [targetProperty]: value }` onto the element with no key-name checking. This produced a very convincing false-alarm "the export doesn't apply data bindings" finding during Phase 4 verification — it reproduced identically in both the pre-built `dist` bundle and the raw `src` runtime, which is what proved it was a bad test input rather than a real bug (a real runtime bug would very likely have behaved differently between the two, or at least wouldn't have been fixed by simply correcting the test's own `targetProperty` string).
9. **Service Workers don't register in the sandboxed Browser pane** — `navigator.serviceWorker.register()` fails with a generic "unknown error occurred when fetching the script" even though the script itself fetches fine (200, correct content-type/content). This blocked `ograf-devtool` entirely, since its own bootstrap hard-requires a successful SW registration before rendering anything past an error page. The same registration succeeds immediately in a real, non-sandboxed Chrome tab (verified via the `claude-in-chrome` MCP surface once the user connected it — see the tool description block near the top of this session's system prompt for how to invoke it). **If a third-party tool your work needs to cross-check against relies on Service Workers, PWA install prompts, or anything else that assumes a "real" top-level browsing context, don't burn time debugging it in the Browser pane — switch to `claude-in-chrome` (asking the user to install/connect the extension if it isn't already) instead.** This is a pane limitation, not specific to this project.
10. **Getting a real exported package onto disk for a tool that expects a local folder (not a zip) means bypassing `showSaveFilePicker()` entirely, not working around it.** `ograf-devtool` wants `window.showDirectoryPicker()`-selected folder containing the manifest + `main.js` as loose files — there's no "upload a zip" path. Combined with gotcha #6 (native pickers can't be automated) and #9 (the Browser pane can't run the tool at all), the working recipe was: build `buildExportArtifacts()` in the _editor's own_ tab via `javascript_tool` (same technique as gotcha #6), pull the `manifest`/`mainJs` strings out through the tool's return value, and write them to disk with `Write`/Node directly — no browser save dialog involved at any point. One trap: if a `javascript_tool` return value is large enough to get redirected to a saved-result file (you'll see a "result exceeds maximum allowed tokens" message with a file path), that file's `text` field is the **JSON-stringified** return value, not the raw string — you need to `JSON.parse()` it once more (or you'll write a file full of literal `\n` escape sequences instead of real newlines, which is syntactically invalid as a `.js` file even though the byte count looks plausible at a glance).
11. **After many rapid source edits + HMR reloads in one session, a `javascript_tool` script's `import('/src/state/projectStore.ts')` (or any other app module) can silently resolve to a _different, disconnected_ module instance than the one the live React app is actually using** — mutating "the store" via the script has zero visible effect in the DOM, even across separate tool calls with real delays in between (this is NOT the same as gotcha #3's same-script batching issue — separating the calls doesn't fix it). Confirmed via the simplest possible probe: call `setProjectMeta({name: 'X'})` on the freshly-imported store and check whether the Menubar's displayed project name actually changes; if it doesn't, this is happening. The fix that actually worked: kill and restart the Vite dev server process entirely (`npm run dev`), then reload the page — a full server restart resets whatever internal module-graph/HMR state had drifted, and dynamic imports and the live app resolve to the same instance again afterward. A plain page reload alone was **not** sufficient once this had happened.
